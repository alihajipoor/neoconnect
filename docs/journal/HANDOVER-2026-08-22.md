# Handover — state of Neoxify as of 2026-08-22

Written to be read cold. If you are a fresh session picking this up,
read this file completely before touching anything. It is the
consolidated state; `docs/journal/windows.md` holds the long-form
narrative and the per-incident detail.

---

## 1. What Neoxify is

A commercial multi-protocol VPN. NestJS backend + Next.js panel + Go node
agent + Tauri clients (Windows desktop, Android/iOS mobile) + a bash
installer. **A large share of users are in Iran, on censored networks.**
That fact decides most of the hard calls: every transport matters,
a silent leak is worse than a visible failure, and "it looks like a VPN"
is itself a defect.

Two machines work on this in parallel — a **Windows** session (desktop
client, backend, panel, installer, Android) and a **MacBook** (iOS only).
Neither sees the other's context, so `docs/journal/` is the only channel
between them. Read `CLAUDE.md` for the ownership table before editing
anything under `apps/mobile/`.

## 4. Every real bug found, and its mechanism

These are the ones worth carrying forward, because each was
counter-intuitive and each cost time.

**Installer could not start (0.9.17).** `Neoxify-Setup.exe` is a Rust
bootstrapper linking `VCRUNTIME140.dll` dynamically. That DLL ships with
the VC++ redistributable, not with Windows, and the bootstrapper runs
*before* anything is installed. On a clean machine it died at the loader
with `/S` hanging forever. Fixed with `+crt-static`, scoped to that crate
only. **This was verified by hashing the download for days before anyone
ran it** — hashing proves the right bytes arrived, never that they run.

**The browser delay (0.9.20).** One silent `continue` in the UDP relay:
a tunnel address is *tentative* for a moment after the adapter appears
(Windows duplicate-address detection), so `bind_upstream` fails and every
datagram in that window was dropped with no log and no retry. DNS is the
first thing any app does, so the resolver burned its 12s budget and gave
up — while TCP sailed through because it retransmits its own SYN far
longer. That asymmetry is why it looked DNS-specific. Now retried.

**The relay ate its own DNS lookups (0.9.23).** `decide()` asked "is this
my own onward socket?" via `OwnerLookup`, which will not rebuild its
snapshot more often than `MIN_REFRESH_INTERVAL` (20ms). An onward socket
is *microseconds* old when it first sends, so inside that window the
answer was "no" and the DNS branch posted the relay's own query back into
the relay. Two lookups closer than 20ms lost **both**. A browser resolves
every asset host at once → text loaded, images did not. Fixed with an
`OwnSockets` registry consulted before any owner lookup, keyed on
**address + port** (an app and the relay legitimately share port numbers
on different addresses).

**Service deadlock (0.9.24).** `/installtunnelservice` returns while its
service is still START_PENDING; `/uninstalltunnelservice` sends a stop
and calls `DeleteService`, but **a START_PENDING service cannot accept a
stop**, so only the delete lands. It then sits RUNNING-marked-for-delete
with nothing that will ever stop it, and the next install spins forever.
Blocked `dispatch` for 25 minutes holding the `Engines` mutex, leaving
the machine full-tunnelled with no way out. Fixed with bounded helpers,
`clear_tunnel_service()`, and **per-request locking** — `status` and
`disconnect` no longer queue behind long operations, because those are
exactly the two things a stranded customer needs.

**Browser showed the real IP for a minute (0.9.25).** Same 20ms window,
different consequence: a SYN arriving inside it gets "unknown owner",
which in `OnlySelected` means *leave it alone*. The SYN goes out
unredirected, **the far end answers it**, and that connection is
established outside the tunnel permanently. 6–22% of new TCP connections
hit it. Now a SYN forces the rebuild — it is the one packet where being
wrong cannot be recovered from.

**IPv6 leaked entirely (0.9.27).** `ip` in a WinDivert filter means
**IPv4 only**. Every IPv6 packet a selected app sent bypassed the tunnel
in the clear while the app said Custom mode was active. Proven on the
wire: 8 packets left, the filter delivered 0, payload readable in
plaintext. Blocked rather than carried — the tunnel adapter has no IPv6
address, so there is nowhere to send them. Customer is told.

**OpenVPN pinned no MTU (0.9.26).** WireGuard pins 1420; OpenVPN had no
equivalent, so the tun came up as wide as the link beneath it. On a
1400-byte path it carried **zero traffic** while printing
`Initialization Sequence Completed`. Sub-1500 links are common in Iran.

**The app tunnelled itself (0.9.22).** In `AllExcept` everything not
excluded is carried, and nobody excludes the VPN client — so its API
calls depended on the tunnel it was managing. 20s spinner, then "can't
reach Neoxify". Now in `own_images` beside the service.

**Four RTL bugs (0.9.25 / android 0.2.15).** The important one: the
Custom-mode toggle knob used physical `left-*`, so in Persian the card
mirrored and the knob did not — **"on" sat exactly where an RTL reader
reads "off"**. A control lying about whether traffic is tunnelled, to
this product's core audience. Invisible in English, shipping for months.
Android has its **own** `PerAppCard.tsx` which carried a verbatim copy of
every one of these — the shared-component assumption does not hold.

**Download/update outage.** A **504 from GitHub** (not a rate limit — the
panel had 46/60 remaining) was cached as `build = null`, indistinguishable
from "no releases", under the *success* TTL with no retry. One failed
request bought a 4½-minute outage of every download link. Third
occurrence. Fixed with retries, a 30s failure TTL, and last-known-good
served for up to 24h. Deployed.

**Installer silently dropped transports.** Trojan and Shadowsocks
defaulted to `skip`; the certificate-stealth *gate* defaulted to no,
dropping VLESS+TLS, VLESS+WS and Trojan on one Enter; an empty domain
aborted `install_xray` entirely; and the role question was offered to
already-enrolled nodes. All fixed.

## 5. Verified state — what has actually been measured

**34 routes, real browser, full tunnel, client 0.9.25:** 32 PASS, 2 SLOW,
**0 failures, 0 failed assets on any route**. Every exit IP read off a
rendered page matched its node. The two SLOW are both OpenVPN
(finland1 6.0 Mbps vs 61.1 on the same node; turkey-1 12.3 vs 52.2).
OpenVPN is the slowest transport fleet-wide by median. Not root-caused.

Upload figures in that run are **floors, not measurements** — a
fixed-size POST on a 200-600ms path is mostly slow start. Download,
latency and page-load are sound.

## 6. Open items, in priority order

1. **Full tunnel may leak IPv6.** `engines/routing.rs` contains **zero**
   IPv6; a plain connect installs only `0.0.0.0/1` + `128.0.0.0/1`. The
   0.9.27 fix does **not** cover this — that block lives in the redirect
   loop, which only runs while Custom mode is on. **This is inspection,
   not measurement.** If it holds it affects every customer. The journal
   names the experiment. **Do this first.**
2. **germany-1's API mirror returns 502.** Not stale DNS —
   `connect.neoxify.com` still resolves to the current panel; it is nginx
   holding a `proxy_pass` address cached from the old VPS.
   `ensure_fallback_site` already writes the fix. **Blocked purely on an
   SSH key** — `ovh_neo`, `azs_vps`, `neo_tr1` all refused.
3. **Rotate credentials.** The turkey-1 root password appeared in the
   chat transcript (key `~/.ssh/neo_tr1` is installed, so it is not
   needed). singapore-1's `agent.json` private key was displayed in a
   terminal during inspection.
4. **XFF / mirror loses the client address on new nodes.**
   `ensure_fallback_site` points the mirror at the Cloudflare-proxied
   panel URL, so `X-Forwarded-For` does not survive. turkey-1 and
   singapore-1 both show it; finland1 and france-1 escape only because
   they predate the panel move. Consequence: one shared rate-limit bucket
   per node, and `/api/health/ip` through a mirror returning the node's
   own address — **which is exactly what a working tunnel looks like**.
   Not fixed: `origin.neoxify.site` preserves the address but the panel
   certificate has no SAN for it, so the "one-line fix" quietly stops the
   mirror hop verifying the panel. Needs a certificate first.
5. **"Welcome to nginx!" on port 80** — singapore-1, turkey-1 and
   germany-1; finland1 does not. nginx arrives for the loopback fallback
   and Ubuntu's default vhost comes with it. A fleet-wide fingerprint
   nobody chose, on a product whose value is not looking like a VPN.
6. **REALITY decoy candidates have rotted into CDNs.** `www.asus.com` and
   `www.leboncoin.fr` both resolve to AWS CloudFront now, and they pass
   `probe_reality_dest` because it tests the handshake and nothing tests
   who owns the address. Fresh names would rot identically — the fix is
   teaching the probe to check ownership.
7. **Direct APK grew 125.8 → 141.2 MB** with no repo change but version
   strings. Unpinned toolchain drift (`rust-toolchain@stable`,
   `gomobile@latest`). That download cost falls on the Iranian users who
   cannot reach Play.
8. **Desktop visual pass not ported to mobile** —
   `apps/mobile/src/screens/Dashboard.tsx` keeps its own status block and
   data-used card.
9. **`reset_selected_connections` closes only ESTABLISHED rows**, so a
   `SYN_SENT` at that instant survives as a direct connection.
10. **Xray REALITY DNS latency** 2.0–5.6s vs WireGuard 0.16s, with no
    clean baseline. Latency at the request level is fine (240ms median),
    so it is DNS-specific and unexplained.
11. **No light theme exists** — `theme.css` defines `:root` and `.dark`
    identically. Relevant before anyone promises one.

Older open tasks still live in the task list: Xray on a real Android
device, relay exit IPs, reconnect-after-disconnect, slow relay
throughput, plans-as-route-sets, the Iran tester's Shadowsocks-only
report, the minimize test, and the three-minute Android connect.

## 7. Rig traps — these cost real hours

**VirtualBox / the test VM (`Neoxify-Test2`)**
- The command is `controlvm <vm> keyboardputscancode` — **singular**. The
  plural is rejected outright. **Never write `>/dev/null 2>&1` over a
  command you are using as a probe** — that typo cost a whole day of
  "the rig is broken" when the tool was saying so on the first call.
- Synthesized keys **never reach the guest when started `--type
  headless`**; use `--type separate`.
- `keyboardputstring` drops a **leading backslash**, so `\\vboxsvr\...`
  arrives as `\vboxsvr\...`. Use the automounted `Z:` drive.
- The Run-dialog session **cannot elevate** — `Start-Process -Verb RunAs`
  returns success and does nothing, so `netsh` and Program Files writes
  fail silently.
- Switching the guest to a **USB keyboard hangs it at the boot logo**;
  this rig's EFI is fragile, which is also why it needs 4 vCPUs. It
  froze twice under host memory pressure at 6144 MB; now at 4096.

**The Windows client on a real machine**
- The service is registered as **`NeoxifyService`**, and runs from
  `C:\Program Files\Neoxify\resources\neoconnect-service.exe`.
  `Get-Service neoconnect-service` returns NOT FOUND while it is plainly
  running.
- The service is LocalSystem in **session 0** and cannot see the
  interactive desktop — `EnumWindows` there returns nothing. Any
  "which windows exist" question must be answered in the app.
- `C:\ProgramData\Neoxify` is ACL'd to LocalSystem; reading the log needs
  elevation.

**Shell and tooling**
- Heredocs in this environment **collapse `\\` to `\`**. Write PowerShell
  and Python files with the Write tool, not heredocs.
- `printf` turns `\a` in `Z:\apps2.ps1` into a BEL byte.
- PowerShell variables are **case-insensitive**: `$svc` and `$SvcExe` are
  the same variable.
- `$L += ...` inside a PowerShell function appends to a *local* copy.
- **Never `2>&1` on a native exe in PowerShell 5.1** — it wraps stderr in
  ErrorRecords and corrupts both body and exit code. This produced 26
  false FAILs in one route matrix.
- The browser automation drives **Edge**, not Chrome.
- A `setInterval` poller in a background tab is throttled to ~1/minute
  and will fabricate a convincing "dead window".

**Two sessions share this worktree.** One switched its branch mid-run
tonight, onto a base predating a fix; committing there would have
silently reverted it. Check `git status` and the current branch before
committing.

## 8. The methodological lesson

The week's failures were nearly all **tests that could not fail**.

- A 40-byte JSON fetch over one connection passed on every route while
  browsers were unusable. It has no concurrency, one lookup, one packet.
- `chrome -> proxy: 0, direct: 60` was reported as proof of a bug. That
  metric **cannot ever** show a redirected connection — the rewrite
  changes the packet's destination while the app's socket keeps the real
  remote address.
- An MTU experiment produced a complete set of plausible numbers
  describing a 1500-byte link while claiming 1400.
- Hashing a download proved the right bytes arrived, never that they ran.

**Six or seven hypotheses died before a test existed that could come back
negative.** Every real fix came from an instrument designed to fail:
packets on the wire, a browser's own reported exit IP, a `pktmon`
capture, an A/B/A with the old binary restored.

Corollary, learned the same way: **a harness reporting total failure is
far more likely to be broken than the thing it measures.**

And the product principle this all serves, from CLAUDE.md: **never report
a tunnel state the app has not verified.** Most bugs this week were a
version of that — a false "Connected", a false "not protected", a
success returned while packets vanished.
